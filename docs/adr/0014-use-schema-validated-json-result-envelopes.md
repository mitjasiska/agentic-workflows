# Use schema-validated JSON result envelopes

Each Managed Agent Pass writes exactly one UTF-8 JSON Result Envelope to an AW-authorized location outside the managed worktree. All roles use one versioned universal schema with a role discriminator and strictly required role-specific payloads, avoiding both duplicated top-level contracts and a flat collection of unrelated optional fields. Implementer outcomes are `ReadyForReview` or `DecisionRequired`; Reviewer outcomes are `Clean`, `ChangesRequired`, or `DecisionRequired`. Warnings and limitations remain orthogonal evidence, not additional outcomes, and agents do not author `Blocked` or `Failed` results. Every role reports a concise summary, detailed narrative, Validation Evidence, and warnings or limitations. Implementers additionally report completed work and resolution of every incoming finding; Reviewers report actionable findings and clean-review public metadata. A decision request identifies the unresolved matter, explains why safe in-scope continuation is unavailable, and proposes a resolution. AW, not the agent, derives changed files and exact repository-state evidence. The complete UTF-8 envelope is limited to 1 MiB; oversized output is rejected with a precise recoverable diagnostic and is never truncated. Raw transcripts, complete diffs, terminal logs, tool-call histories, and binaries remain outside SQLite, with bounded descriptions and stable external references used when necessary. The envelope is correlated to the expected pass and contains typed evidence and detailed human-readable narrative fields. Deterministic workflow code validates it before routing, so malformed, missing, ambiguous, or inconsistent agent output cannot authorize success. When normal turn completion is positively confirmed but the envelope is missing or invalid, AW records a recoverable Failed Operation with a specific contract diagnostic, preserving the worktree, session, and evidence. The complete validated envelope is stored immutably in SQLite as durable pass evidence, together with a typed relational projection of fields needed for routing and queries. Both are created from the same validated object in one transaction and are not independently editable; the temporary JSON file is transport only. During pre-stable development, the installed build accepts and reads only its current envelope schema version; it neither carries legacy readers nor rewrites historical JSON. Backward-compatible history is deferred until an explicit stabilization milestone. This preserves the prototype's proven JSON delivery mechanism without freezing a rapidly changing contract prematurely.
