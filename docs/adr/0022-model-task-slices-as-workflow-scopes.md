# Model Task Slices as workflow scopes

A Task may be delivered through multiple independently submitted Workflows. AW represents it as one Project-level provider-neutral identity while any sibling Workflow remains retained. Every Workflow carries one scope value: `WholeTask` or `NamedSlice(name)`. A named Task Slice is not a separate aggregate, identity, lifecycle, or requirements document; it is a user-declared, agent-visible scope label stored on the Workflow. Each Workflow owns its own immutable Task Snapshots, branch, worktree, implementation/review loop, Review Target, and pull request while retaining provenance to the shared parent Task. Siblings never share an active snapshot or mutable workflow state. Cleaning the final retained Workflow removes the now-unreferenced Task record, so this relationship does not create a permanent Task registry or tombstone. A Task may retain Whole Task and Named Slice Workflows together. Starting a later Workflow captures the then-current Task Source but does not supersede, repartition, or reinterpret earlier Workflows, and AW does not attempt to prove that their scopes are non-overlapping. `awctl start` never silently reuses an existing worktree: if the same Task and scope already has a retained Workflow, it stops without mutation and reports the explicit continuation choices. Changed Linear requirements are adopted only by explicitly resuming that Workflow. Once it owns a pull request, a separate pull request for the Task requires a distinct named scope through `--slice`. For Linear, branch identity uses the stable Issue key plus the optional normalized slice name and excludes the mutable title. Explicit cleanup permits later reuse of the same scope only after the retained Workflow and its exact local branch are gone and no live candidate branch remains on the configured remote. This preserves the prototype's useful one-task-to-many-PR behavior without introducing a Task Slice subsystem or risking accidental abandonment of unfinished work. The ordinary default remains one Task, one `WholeTask` Workflow, and one pull request.
