# Model Task Slices as workflow scopes

A Task may be delivered through multiple independently submitted Workflows. Every Workflow carries one scope value: `WholeTask` or `NamedSlice(name)`. A named Task Slice is not a separate aggregate, identity, lifecycle, or requirements document; it is a user-declared, agent-visible scope label stored on the Workflow. The complete Task Snapshot remains authoritative, and AW does not mechanically enforce the semantic boundary. The Workflow owns one branch, worktree, implementation/review loop, Review Target, and pull request while retaining provenance to the parent Task and its Task Snapshots. A Task may retain Whole Task and Named Slice Workflows together. Starting a later Workflow captures the then-current Task Source but does not supersede, repartition, or reinterpret earlier Workflows, and AW does not attempt to prove that their scopes are non-overlapping. `awctl start` never silently reuses an existing worktree: if the same Task and scope already has a retained Workflow, it stops without mutation and reports the explicit continuation choices. Changed Linear requirements are adopted only by explicitly resuming that Workflow. Once it owns a pull request, a separate pull request for the Task requires a distinct named scope through `--slice`. For Linear, branch identity uses the stable Issue key plus the optional normalized slice name and excludes the mutable title. This preserves the prototype's useful one-task-to-many-PR behavior without introducing a Task Slice subsystem or risking accidental abandonment of unfinished work. The ordinary default remains one Task, one `WholeTask` Workflow, and one pull request. Concurrent execution and later reuse of the same scope are separate policy decisions.
