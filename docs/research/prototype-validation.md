# Prototype validation behavior

Research target: [`mitjasiska/agentic-workflows-prototype`](https://github.com/mitjasiska/agentic-workflows-prototype) at `main` revision [`677bfcb92bb733e832bf89bfd2931ab0b6e76784`](https://github.com/mitjasiska/agentic-workflows-prototype/commit/677bfcb92bb733e832bf89bfd2931ab0b6e76784), inspected on 2026-10-17. This report uses only the prototype's source, tests, and documentation.

## Bottom line

The prototype does **not** have a deterministic test-selection or validation-command engine. The workflow injects validation policy into agent handoffs; implementers and reviewers choose and run commands, then return structured evidence. The controller deterministically validates the result shape and decides whether the loop may continue. The documentation explicitly calls the command-execution policy prompt guidance rather than controller-enforced proof ([lifecycle policy](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/docs/lifecycle.md#L709-L726)).

The prototype's current treatment of an underlying or pre-existing test failure explains the reported friction: an implementer may diagnose the same failure on the pinned base, but the executed failure must remain `failed`, and an implementation result containing any failed check cannot be `completed`. The pass therefore reports `blocked`, the loop escalates, and review does not start automatically ([implementation instructions](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/handoff.py#L11-L24), [implementation result gate](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/implementation_pass.py#L60-L92), [loop routing](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/loop.py#L226-L271)).

## Confirmed behavior

### Structured result transport

- An implementation pass instructs the agent to write exactly one UTF-8 JSON object to a temporary `result.json` outside the checkout. The controller parses it with duplicate-key rejection and requires the exact fields `pass_id`, `state`, `summary`, `checks`, and `resolutions`, plus conditional task-assessment data when enabled ([implementation result delivery and parser](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/implementation_pass.py#L51-L151)).
- A review pass uses the same outside-checkout JSON delivery pattern with a different strict schema: `pass_id`, `state`, `summary`, `findings`, and `checks`, plus publication metadata when applicable ([review result delivery](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/handoff.py#L303-L313), [review parser](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/review_result.py#L111-L177)).
- The prototype therefore already separates machine-significant fields from human-readable `summary` prose. Its implementation and review schemas are role-specific rather than one universal result shape.

### Focused test selection and TDD

- Implementers are told to create thorough behavioral, regression, edge-case, failure-path, and invariant tests, but to execute focused subsets: new or changed tests, directly affected components, and concrete shared-contract or integration boundaries. Broader or repeated execution is reserved for changed code, new failures, unresolved risks, or explicit requirements. TDD/red-green-refactor is useful but optional ([handoff instructions](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/handoff.py#L28-L47)).
- Reviewers inspect the full diff but choose targeted and adversarial checks based on risk. They may independently rerun an implementer's test when confirmation is warranted, but should not repeat long overlapping suites merely to accumulate evidence ([review instructions](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/handoff.py#L83-L119)).
- There is no affected-test algorithm, test manifest, or controller-selected command in this path. The agent exercises judgment from the task, repository instructions, diff, and existing evidence. This is also how the canonical policy describes the implementer/reviewer responsibilities ([validation guidance](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/docs/lifecycle.md#L624-L640)).
- The only validation strategy setting is reviewer-side `review.validation.strategy`. It accepts `focused_first` or `exhaustive`, defaults to `focused_first`, and rejects other values before execution ([configuration parser](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/config.py#L41-L44), [validation parser](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/config.py#L137-L146)). There is no configurable TDD methodology setting ([configuration documentation](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/docs/configuration.md#L536-L556)).

Under `focused_first`, both finding and clean review passes use focused checks; a nearly clean review does not trigger the full suite. Under `exhaustive`, every review pass runs full validation, including a findings pass. Explicit task/repository requirements override either strategy ([strategy prompts](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/handoff.py#L121-L131), [lifecycle description](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/docs/lifecycle.md#L661-L677)). The setting controls review, not implementation; implementation always receives the focused-execution guidance.

### Structured validation evidence and gates

| Phase | Structured outcome | Check schema | Acceptance rule |
|---|---|---|---|
| Implementation | `completed`, `blocked`, or `failed` | Exact fields `name`, `result`, `details`; result is `passed`, `failed`, or `not_run` | `completed` is rejected if any check is `failed`; fix completion also requires one resolution for every supplied finding. `not_run` is allowed when reported honestly. |
| Review | `clean`, `findings`, `blocked`, or `failed` | `name`, `result`, `details`, plus optional `scope` of `review` or `merge` | `clean` cannot contain findings or failed checks. Required review-scoped checks need independent passing evidence. `findings` requires at least one finding. |

The implementation contract and parser enforce the first row ([result handoff](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/implementation_pass.py#L123-L151), [parser](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/implementation_pass.py#L60-L92)). The reviewer contract and parser enforce the second ([review result handoff](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/handoff.py#L303-L313), [verdict parser](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/review_result.py#L111-L177)).

Neither normal parser globally requires a nonempty check list or at least one passed check. A `completed` implementation or `clean` review with `checks=[]` is structurally possible when no carried review requirement applies. Whether a check was mandatory is therefore supplied through task/repository instructions and reviewer classification; the controller does not derive mandatory commands from the diff.

Review check scope is meaningful:

- `scope=review` means passing evidence is required before a clean review.
- `scope=merge` may remain `not_run` and visible as a limitation when policy permits deferral.
- A previously failed check becomes outstanding review evidence and cannot be demoted or silently omitted; later clean acceptance requires an independently reported pass under the same check name ([pending-check logic](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/review_result.py#L60-L102)).

The tests confirm that `completed`/`clean` may carry an honest pending `not_run` merge-time regression, while either parser rejects a failed check presented as completed/clean ([contract tests](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/tests/test_validation_policy.py#L167-L185)).

### What happens when a test fails

The controller does not intercept a test command and terminate the agent at the instant it returns nonzero. Test execution happens inside the nondeterministic agent pass. The agent may investigate, perform the pinned-base comparison, and then writes its structured result. The deterministic stop happens when that result is accepted and routed.

**During implementation:**

- Any executed failed check makes `completed` invalid. The handoff explicitly instructs the implementer to return `blocked`, even when the identical failure reproduces on the pinned base and appears unrelated ([handoff](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/handoff.py#L35-L45)).
- A structured `blocked` or `failed` result puts the loop into `escalated` and removes the next automatic phase, so no reviewer is launched ([route function](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/loop.py#L226-L271)).
- Loop tests confirm both sides of that gate: a completion claim containing a failed check escalates without a review prompt, and an explicitly blocked implementation reports human action with no review ([loop tests](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/tests/test_loop.py#L732-L748)).
- The regression test deliberately models this case: focused tests pass, another check fails, and the same failure is observed on the pinned base. It verifies that `blocked` is accepted but changing it to `completed` is rejected ([baseline-failure test](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/tests/test_validation_policy.py#L187-L228)).

**During review:**

- A failed test that demonstrates an in-scope implementation defect may accompany a `findings` verdict. The normal loop can send the full findings batch to the implementer. The failed check is retained as required review evidence until an independent re-review records it passing ([failed-check routing tests](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/tests/test_validation_policy.py#L345-L377)).
- If mandatory validation is unavailable (`not_run` with review scope), or an unrelated baseline failure has no authorized in-scope correction, the reviewer is instructed to return `blocked`, not `clean`. If a reviewer returns findings while a required check remains unavailable, the parser changes the effective result to `blocked` while preserving the findings and check evidence ([review instructions](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/handoff.py#L96-L118), [parser conversion](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/review_result.py#L154-L164)).

### Baseline comparison and recovery friction

For a possibly pre-existing failure, both roles are instructed to run the same command against the pinned unchanged base when safe and proportionate, using disposable state outside the task checkout. They must record both results, the base SHA, and environment differences. If comparison is impractical it is `not_run` and the cause remains unverified. A matching base failure supports diagnosis but is explicitly not proof that the changed tree is safe ([baseline instructions](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/handoff.py#L11-L24), [policy](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/docs/lifecycle.md#L709-L722)).

Recovery is explicit rather than automatic:

- Blocked implementation evidence stops the run. `--new` is allowed to replace eligible stopped implementation checkpoints; it reuses the verified existing implementation context, whereas completed blocked review evidence is specifically protected from `--new` ([new-run control](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/loop.py#L793-L813), [context reuse and new state](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/loop.py#L843-L901)).
- A completed blocked review requires the human to resolve the external prerequisite and run `awp loop ISSUE --retry-review`. With implementation findings, the workflow then sends saved findings/checks to the implementer; without findings it retries reviewer validation directly. A further blocked result requires another explicit retry ([blocked-review continuation](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/docs/lifecycle.md#L995-L1033)).
- The pane, pass evidence, and session identity are preserved across a block, timeout, or interruption, but the single-pass review command still requires human action for blocked validation ([review lifecycle](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/docs/lifecycle.md#L809-L838)).

This is the prototype's main validation-friction point: baseline triage improves diagnosis, but it does not change the hard completion gate. Even an unrelated failure reproduced on the base forces an implementation stop and an explicit recovery action before independent review can occur.

### Linting and type checking

Linting is not a first-class deterministic workflow phase in the prototype. The implementation handoff asks the agent to run “proportionate inexpensive syntax/lint/diff checks,” but does not name a linter or a configured command ([handoff](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/handoff.py#L35-L42)). The tracked `pyproject.toml` defines build, project, scripts, and setuptools metadata only; it has no linter or type-checker configuration ([pyproject](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/pyproject.toml#L1-L30)). No first-class type-check step was found.

The deterministic GitHub Fast PR workflow runs `git diff --check` and a fixed selected `unittest` command; it does not run a linter or type checker ([Fast PR workflow](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/.github/workflows/pr.yml#L32-L69)). Nightly CI runs the complete offline unittest suite ([nightly workflow](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/.github/workflows/nightly.yml#L29-L42)). The architecture documentation describes these as separate Fast PR and nightly/full-regression gates and notes there is no test-selection engine in CI ([CI documentation](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/docs/architecture.md#L568-L633)).

## Existing worktree and pull-request discovery

### Worktree selection and reuse

`awp start ISSUE [--slice NAME]` loads the current Linear issue, derives a proposed branch from the issue identifier plus the normalized slice or current title, and calls the shared preparation path ([CLI](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/cli.py#L166-L212), [branch naming and preparation](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/preparation.py#L27-L48)). An explicit slice selects that exact branch. Without `--slice`, any branch equal to the issue ID or beginning with `issue-id-` is eligible, so one unambiguous old-title branch—or even one branch originally created as a slice—can be reopened after the issue title changes ([selector](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/workspace.py#L979-L1018), [slice continuity test](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/tests/test_lifecycle.py#L362-L410)).

Selection combines four sources of evidence:

- local branches from `git for-each-ref`;
- registered Git worktrees from `git worktree list --porcelain -z`;
- Herdr registrations from `herdr worktree list --cwd REPO`; and
- live branches from `git ls-remote --heads` against every configured remote. Cached `refs/remotes/*` do not count ([Git discovery](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/workspace.py#L177-L197), [combined resolution](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/workspace.py#L991-L1052)).

Reuse requires exactly one local branch, one Herdr entry, and one Git worktree to agree on branch and canonical path. The checkout must exist and be linked, attached, non-bare, non-prunable, and unlocked; it cannot be the permanent checkout. A branch-only, remote-only, mismatched, or multi-candidate state fails instead of being repaired or guessed. Tests cover title-change reuse, branch-only and remote-only refusal, duplicate Herdr entries, and unusable Git worktrees ([reuse tests](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/tests/test_task_start.py#L404-L501)).

Preparation claims and locks the initial selection before updating the shared base, resolves again afterward (now including live remotes), and rechecks once more under admission; a changed selection aborts ([claim and recheck](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/workspace.py#L1054-L1093)). New state is created with `herdr worktree create`; reuse calls `herdr worktree open --path ... --label ... --focus`. The returned Herdr workspace/tab/pane identity and Git registration are verified, including preservation of an existing open workspace ID ([open/create and confirmation](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/workspace.py#L1095-L1144)).

Default-versus-slice identity is not inferred from the mutable title or Herdr label. It is stored as `agentic-workflows-scope.json` in the linked worktree's private Git directory, with exactly version, issue identifier, branch, and slice (`null` for default). The record is created immutably and never overwritten. A legacy worktree with no record requires an explicit matching `--slice` before reuse ([scope implementation](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/workspace.py#L681-L729), [scope tests](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/tests/test_lifecycle.py#L414-L468)).

`awp review` and `awp pr` reuse the same local resolver but require an exact existing, open Herdr task worktree and consistent context identities; they do not create or repair one ([review/publication resolver](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/review.py#L31-L58)). The CLI exposes `--slice` only on `start`; review and `pr` accept only the issue identifier for workspace selection ([start parser](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/cli.py#L38-L44), [review parser](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/cli.py#L77-L82), [PR parser](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/cli.py#L116-L125)). Multiple local task/slice candidates therefore make issue-only review/publication ambiguous.

### PR lookup and state handling

PR identity is based on the selected repository and branch, not directly on the Linear issue. The prototype does not use `gh pr list`, `gh pr view`, or `gh api`: `gh` is only an optional credential source via `gh auth token --hostname github.com`. Credential precedence is `GH_TOKEN`, then `GITHUB_TOKEN`, then the local `gh` credential, then anonymous access for reads; writes require a credential ([credential code](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/github.py#L43-L85)). GitHub operations use direct HTTPS REST requests to `api.github.com` ([request code](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/github.py#L164-L196)).

The lookup enumerates `GET /repos/{repo}/pulls?state=all&head={repo-owner}:{branch}&per_page=100&page=N`, for at most 20 pages. Every response must name the expected branch and same repository on both head and base sides ([enumeration and validation](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/github.py#L301-L331)). Consumers interpret the same history differently:

| Consumer | No PR | Open PR | Closed, unmerged PR | Merged PR |
|---|---|---|---|---|
| `awp start` history guard | Allow selection | Allow selection | Refuse as historical | Refuse as historical |
| `awp pr` | Create, unless a recorded PR number says that PR must exist | Reuse only one exact open PR | Refuse as conflict | Refuse as conflict |
| merged-cleanup proof | Insufficient | Insufficient | Insufficient | Accept only one exact, positively verified merge |

Before both new-branch creation and existing-worktree reuse, `start` checks all returned history and rejects any entry whose state is closed or whose `merged_at` is non-null. It does not require a unique open PR, validate an open PR's base branch or head SHA, or persist whether the result was “absent” versus “open”; either permits the workspace. For an existing workspace, all configured remotes must resolve to the same GitHub repository. A non-GitHub remote permits a new workspace without a PR-history check but refuses reuse because history cannot be established ([history guard](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/github.py#L334-L347), [remote consistency](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/workspace.py#L199-L219), [state tests](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/tests/test_lifecycle.py#L208-L280)).

`awp pr` is stricter. Zero results authorizes creation only when no durable PR number is expected. One result is fetched again by number; list and detail must agree on number, repository, head branch/SHA, configured base, open state, unmerged state, and canonical URL. More than one result, or a closed, merged, wrong-base, wrong-head, wrong-repository, changing, or previously recorded-but-now-missing PR, refuses publication. A valid existing PR is reused and PATCHed only if title/body differ; an uncertain write is recovered by rerunning `awp pr`, which enumerates history before another write ([exact publication lookup](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/github.py#L236-L298), [retry tests](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/tests/test_publish.py#L170-L230), [conflict tests](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/tests/test_publish.py#L782-L802)). Native `git ls-remote` separately verifies the live base and task-branch SHAs before push and GitHub writes ([remote-ref code](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/publish.py#L68-L125), [publication sequence](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/publish.py#L562-L680)).

The private `agentic-workflows-publication.json` stores the durable task/repository binding, publication lineage, frozen heads, cycle state, and eventually the PR number—not a cached live open/closed/merged status ([schema](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/publication_state.py#L22-L84), [store location](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/publication_state.py#L111-L115), [default and legacy reads](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/publication_state.py#L198-L215)). `awp status` projects that saved number and publication state without refreshing GitHub, so it cannot by itself reveal that an open PR was later closed or merged ([status projection](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/status.py#L551-L590)). Cleanup has a separate positive proof: exactly one PR, agreeing list/detail responses, exact base and head SHA, `merged is true`, closed state, non-null merge time, valid merge commit, and local-base reachability ([merge proof](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/github.py#L350-L377), [local reachability](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/workspace.py#L221-L266)).

Confirmed limits and ambiguities: the GitHub query covers only same-repository PRs whose head owner is the base repository owner, so fork/cross-repository PR history is outside this identity model; enumeration is capped at 2,000 results; `start` treats absent and any number of all-open PRs alike; and no `--slice` selector exists for review/publication. These are descriptions of the prototype's boundaries, not recommended architecture decisions.

## Linear labels and generated publication metadata

The optional task-authoring skill uses a closed classification vocabulary: one task kind from `implementation`, `research`, or `experiment`; at most one primary category from `feature`, `bug`, `chore`, `docs`, or `refactor`; and an independent Research modifier. Primary categories map exactly to `Feature`/`feat`, `Bug`/`fix`, `Chore`/`chore`, `Docs`/`docs`, and `Refactor`/`refactor`; Research adds only the `Research` label. Pure research therefore has no change type unless it also has a primary category ([classification constants and configuration validation](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/skills/create-linear-task/scripts/prepare_issue.py#L19-L27), [intended-label derivation](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/skills/create-linear-task/scripts/prepare_issue.py#L310-L365), [research cases](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/tests/test_linear_task_skill.py#L426-L459)).

Label reconciliation is deliberately scoped. The preparer resolves the complete six-label canonical catalog by exact name, adds missing intended workflow labels, and never submits a replacement set containing unrelated labels. Existing unrelated labels are preserved. Stale canonical workflow labels stop preparation by default; a per-project `replace_workflow_labels = true` permits removing only those stale canonical labels. The skill re-reads labels immediately before mutation and verifies the exact canonical set afterward rather than silently repairing a concurrent change ([preparation algorithm](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/skills/create-linear-task/scripts/prepare_issue.py#L475-L533), [post-mutation verification](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/skills/create-linear-task/scripts/prepare_issue.py#L540-L566), [preservation and replacement tests](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/tests/test_linear_task_skill.py#L482-L578)).

Publication independently reads the current Linear labels; it does not trust the `Change type` prose rendered into the issue description. Exactly one recognized primary label must resolve to a Conventional Commit-style type. `Research` and unrelated labels are ignored for type selection, while no primary label or multiple primary labels refuse publication before a commit or durable publishing intent is created ([runtime type selection](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/publish.py#L31-L38), [no-side-effect failure test](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/tests/test_publish.py#L813-L821)).

The reviewer—not the Linear issue title—produces three public-safe fields from the actual reviewed implementation: a concise action summary, description, and validation statement. The summary must be a single lower-case action phrase with no type prefix, issue suffix, doubled whitespace, or sentence-ending punctuation; its identifier-dependent limit reserves enough space for the final subject to remain within 72 characters. Descriptions and validation are limited to 2,000 characters and may not contain Markdown headings. Missing or stale public metadata requires a new review; publishing never falls back to the possibly stale task title or private findings ([review handoff contract](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/handoff.py#L272-L301), [metadata validator](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/review_result.py#L12-L38), [fallback refusal test](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/tests/test_publish.py#L1888-L1896)). The Linear issue title itself remains user-authored; task preparation only requires it to be nonempty and one line ([task renderer](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/skills/create-linear-task/scripts/prepare_issue.py#L440-L463)).

Deterministic publication combines that evidence into both the PR title and commit subject as `<type>: <reviewed action summary> (TEAM-123)`. The PR body has exactly `Summary`, `Tracking`, and `Validation` sections, followed by the statement that independent task review accepted the exact change. `Tracking` contains a canonical linked Linear identifier. It does **not** emit `Closes`, `Fixes`, or another auto-closing reference. The full commit message adds a blank line and `Task-Review: <pass-id>` trailer beneath the shared subject ([metadata assembly](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/publish.py#L213-L221), [commit intent](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/task_start/publish.py#L515-L535), [end-to-end assertions](https://github.com/mitjasiska/agentic-workflows-prototype/blob/677bfcb92bb733e832bf89bfd2931ab0b6e76784/tests/test_publish.py#L87-L101)).

Worth preserving: the small canonical category-to-type mapping, optional orthogonal Research label, protection of unrelated labels, deterministic title/body assembly from independently reviewed public metadata, identical PR/commit subjects, and refusal to copy the task title as a fallback. Prototype friction to reconsider rather than inherit automatically: preparation requires all six canonical labels to exist even when only one is used; stale canonical labels block by default unless replacement is configured; and a pure-research issue with no primary category cannot use `awp pr`. An auto-closing PR reference would be new behavior, not preservation of the prototype.

## Inferences and design lessons, not prototype guarantees

1. **The prototype separates evidence truth from command execution, but partly couples evidence truth to routing.** Preserving an executed failure as `failed` is an evidence-integrity rule. Refusing to continue to review after a confirmed unrelated implementation failure is an additional routing choice. The code currently couples them; they need not be treated as the same future design decision.
2. **“Focused” is a policy word, not a deterministic selection mechanism.** The prototype gives agents sound heuristics, but it cannot prove that the most relevant subset was chosen. Any future deterministic test selection would be new behavior, not preservation of the prototype.
3. **Review handles actionable failures with less friction than implementation.** A reviewer can use a failing test as evidence for an implementation finding and continue the fix/re-review loop. An implementer with an unrelated baseline failure must stop before the first review. That asymmetry is confirmed behavior and a useful target for later discussion; this report does not decide whether to keep it.
4. **Lint/type-check ownership is still open.** In the prototype, lint-like checks are agent-selected evidence unless a task or repository instruction makes them explicit; CI does not establish a general lint/type gate. Deciding that lint is always deterministic, always agent-run, or always blocking would be a new architecture decision.
5. **The result schema cannot establish that a command actually ran.** It validates honest, well-shaped claims and carries evidence forward, but the documentation explicitly says execution proof is not controller-enforced. Adding command receipts, logs, or workflow-owned execution would introduce a stronger contract and more machinery.
