# Adopt JSON-RPC 2.0 for the Local Control Interface

Accepted under DEV-122 on 2026-10-24 as a Design Direction refinement of [ADR 0037](0037-use-platform-local-ipc-for-awctl.md).

The Local Control Interface uses JSON-RPC 2.0 through an established .NET implementation instead of the initial custom JSON envelope. This gives subsequent methods a common request identity, method, result, and error model without building another RPC implementation. JSON-RPC is transport-independent; adopting it does not introduce HTTP or network administration. The existing platform-local, same-OS-account boundary, bounded exchanges, and application-layer independence remain Product Invariants. Accepted Operations remain owned by the control plane after client disconnection.

The JSON-RPC `"jsonrpc":"2.0"` marker describes the message standard. AW carries its application protocol version separately and validates it before method lookup, application parameter binding, or execution of any command or query. Pre-stable builds require an exact application-version match, with both versions and update/restart guidance in a structured mismatch diagnostic. They neither negotiate cross-version compatibility nor promise a stable third-party API. The superseded custom envelope is not retained as a second protocol.

This change exposes only `status`. Notifications, batches, subscriptions, streaming, and further workflow methods are not product capabilities. Queries return projections in `result`; failures use `error`, with AW diagnostics in `error.data` where applicable. Exact method names, framing, error codes, and connection lifetime remain Implementation Latitude within these constraints.

## Implementation evidence and selection

Microsoft StreamJsonRpc 2.26.150 is selected. Its [maintained NuGet package](https://www.nuget.org/packages/StreamJsonRpc/2.26.150) was released on 2026-10-19. Its documented [message-handler extension point](https://microsoft.github.io/vs-streamjsonrpc/docs/extensibility.html) supports Unix socket streams and separates framing from JSON-RPC dispatch. [EdjCase.JsonRpc.Router](https://www.nuget.org/packages/EdjCase.JsonRpc.Router/6.1.0) was also considered: its ASP.NET routing focus makes it a less direct fit for this non-HTTP stream adapter.

StreamJsonRpc supplies serialization, request correlation, parameter binding, method dispatch, and standard method/parameter errors. Its general-purpose defaults need a narrow local profile: the formatter accepts legacy protocol markers, the built-in length handler does not impose AW's 16 KiB limit, and the connection normally permits multiple messages. AW therefore uses the library's `MessageHandlerBase` extension point to retain bounded four-byte length framing, validate the 2.0 marker and message shape, apply the universal application-version gate, and admit one request per connection. This is framing and admission policy around the library, not a replacement RPC dispatcher. Source inspection of [LengthHeaderMessageHandler](https://github.com/microsoft/vs-streamjsonrpc/blob/v2.26.150/src/StreamJsonRpc/LengthHeaderMessageHandler.cs) and [SystemTextJsonFormatter](https://github.com/microsoft/vs-streamjsonrpc/blob/v2.26.150/src/StreamJsonRpc/SystemTextJsonFormatter.cs) establishes these defaults.

A five-second deadline covers connection and I/O; caller cancellation closes the exchange locally. The library's cancellation-notification extension is disabled, and connection closure is not configured to cancel application methods. Parser and frame failures receive standard JSON-RPC errors where a reply can be sent; disconnected or stalled exchanges close within their deadline. Unexpected handler failures use an internal-error response without serialized CLR exception details. Real-socket tests cover these boundaries, correlation, library-client interoperability, and zero application dispatch for incompatible versions. Existing endpoint and process tests continue to exercise permissions, ownership, recovery, and cleanup.

The [implemented contract](../../reference/local-control-interface.md) records the precise Linux wire profile. Windows/macOS transport implementation and any remote administration model remain separate work.
