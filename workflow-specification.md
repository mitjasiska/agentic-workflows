# Agentic Workflows Workflow Specification

> Living specification created during the architecture refinement session on October 17, 2026.
>
> This document is the canonical source for detailed workflow mechanics. `architecture.md` owns current product boundaries and architectural shape, `GLOSSARY.md` owns canonical language, and ADRs preserve durable decision rationale. A conflict among them is a documentation defect to reconcile, not an implementation choice.

## 1. Product and reference conventions

- The canonical CLI executable is `awctl`.
- Most task definitions originate in Linear.
- A task definition may alternatively come from a Markdown file or pasted text.
- The Initial E2E Milestone supports Linear as its sole Task Source. Markdown files and pasted or standard-input text are the first source expansion immediately after that milestone, before broader v1 provider and workflow expansion.
- The Initial E2E Milestone completes the full managed cycle through an explicit `awctl pr`: deterministic commit, push, and GitHub pull-request creation are part of the milestone, while merge remains a separate human action. Acceptance comes from end-to-end tests of the complete cycle. Using the new system to develop Agentic Workflows itself may begin later and is not a prerequisite for this milestone; development may continue through the existing prototype until the successor is ready.
- The first submission milestone creates a new GitHub pull request. Adding another reviewed commit to that open request is an immediate post-milestone expansion, alongside Markdown and pasted/standard-input Task Sources; it is not deferred to late v1.
- End-to-end coverage never requires introducing a defect into genuine implementation work merely to force a repair cycle. Clean-first review is a valid real result. Findings-to-repair routing is exercised with controlled workflow tests and synthetic Result Envelopes; naturally occurring findings may exercise the same path during later real use.
- v1 integrates Linear and GitHub. Jira and GitLab are possible later adapters, not v1 implementations; the initial design preserves narrow provider boundaries without building a generalized multi-provider framework.
- AW automatically moves a Linear Task to the configured In Progress state during Workflow startup; the user is not expected to perform that transition manually. Project setup resolves and saves the concrete Linear workflow-state identifier. It automatically selects an unambiguous active-work state when possible and requests a one-time choice only when resolution is ambiguous; task runs do not repeatedly search by the English label. Startup validates that the saved state still exists for the Task's team. A read-only admission check stops without creating a Workflow or worktree when the Task is already in a terminal Done or Canceled state; the user must deliberately reopen it in Linear before retrying. An existing configured In Progress status is an idempotent success. The remaining deterministic order is: durably prepare the Workflow and worktree, update Linear when required, and then launch the first agent. A failed Linear update stops startup before agent launch and leaves the prepared Workflow available for retry. A successful Linear update followed by an agent-launch failure leaves the Task In Progress and the Workflow available for retry; AW does not attempt a compensating status rollback. After this startup responsibility, AW observes and reports later Linear status changes but does not write or reassert a status. `awctl pr` does not mark the Task Done. The existing GitHub–Linear integration owns later PR-driven transitions, including completion when the pull request is merged. AW does not treat provider status as proof of workflow or submission correctness.
- If an active Task later becomes Canceled in Linear, AW allows a currently running Managed Agent Pass to finish and preserves its work and result, then pauses before the next managed handoff for an explicit user decision. If no pass is running, the pause applies when AW observes the cancellation. AW does not automatically interrupt the agent or reopen the Task. The user may still stop immediately with Ctrl+C or exit the agent, after which the normal interruption and recovery behavior applies.
- If an already-active Workflow observes that its Linear Task became Done, AW records and displays a warning but continues without pausing or changing the Task status. A sibling pull request may have caused the automatic transition before this Workflow created its own request, so Done is not reliable evidence of an intent to stop active work. Canceled remains distinct and follows the handoff-pause rule above.
- [Agentic Workflows Prototype](https://github.com/mitjasiska/agentic-workflows-prototype) is the behavioral reference. The new product should preserve its proven workflow value while deliberately removing the friction discovered through its use; it is not a class-for-class or command-for-command port.

### 1.1 Immutable, versioned task snapshots

When a Workflow begins, AW captures the Task Definition and its provenance as its first immutable Task Snapshot. Every agent pass records the exact Task Snapshot it received.

For every textual Task Source, the authoritative requirements and source-change fingerprint are selected deterministically:

- When a recognized `Agent instructions` section exists, its captured contents are the authoritative agent-facing requirements. The remaining source content is retained as human-facing context and provenance.
- When `Agent instructions` is absent, the complete captured task content is authoritative.
- Changes outside the authoritative requirements content do not create a new Task Snapshot, pause the Workflow, or alter what later agents receive from the already selected snapshot.
- AW does not use an agent or semantic heuristic to decide whether a requirements change is material. Any changed authoritative content produces a different fingerprint and triggers the handoff-boundary decision.

Linear is expected to use `Agent instructions` for durable development work. Markdown files and pasted text are intended for quick work, such as researching a Git repository and producing a PDF report, so their complete contents will usually be authoritative.

The same missing-section policy applies to every textual source, including a README used as a Markdown task file:

- `warn` is the default. AW emits a prominent warning and continues automatically with the complete captured content as the authoritative requirements.
- `require` refuses to create or adopt the Task Snapshot and does not start the next agent pass until the section is supplied or the policy is explicitly overridden.
- `ignore` silently continues with the complete captured content as the authoritative requirements.

This uniform policy avoids source-specific workflow paths. For a Linear-backed Task, AW additionally captures the Issue identifier, title, complete description, extracted `Agent instructions` section when present, and available source provenance.

Linear and Markdown file sources can be checked again at handoff boundaries. Pasted text and standard input are immutable after capture because AW has no external source to re-read.

For a Task captured from a Linear Issue, later edits to the Issue do not silently alter or automatically interrupt the running pass. The user may still interrupt manually, including with Ctrl+C; recovery from manual interruption is specified separately. Before AW performs the next agent handoff, it compares the source with the latest source revision already handled by the Workflow. If the source changed, AW pauses and offers three choices:

1. Continue using the active Task Snapshot. This acknowledges that exact source revision, so AW does not ask about it again unless the source changes again.
2. Adopt the changed source as a new immutable Task Snapshot in the same Workflow. All earlier snapshots remain in history.
3. Stop without performing another handoff.

Adopting a new Task Snapshot invalidates prior conclusions that depended on the previous requirements. The next agent phase is always implementation, even when review would otherwise have followed, because the existing implementation has not yet addressed the new snapshot. The selected Implementer receives the complete new snapshot and relevant existing workspace and finding context. Review may resume only after implementation completes against that same snapshot.

This deliberately differs from the prototype behavior in which implementation and review may each read the latest Linear Issue. Versioned immutable snapshots prevent an Implementer from working against one set of requirements while a Reviewer judges the result against another, while still allowing the user to adopt changed requirements without discarding the Workflow and worktree. Source edits never retroactively change a completed or submitted Workflow. A later Workflow for the same Task captures the then-current source as its own initial Task Snapshot.

### 1.2 Task Slices and multiple pull requests

One Task may produce multiple pull requests through independent Workflows. Every Workflow has one scope value: `WholeTask` or `NamedSlice(name)`. A named Task Slice is therefore Workflow scope rather than a separate aggregate or lifecycle. Each Workflow owns one branch, worktree, implementation/review loop, Review Target, and pull request. Sibling Workflows retain provenance to the same parent Task and its Task Snapshots, but their mutable workspace state and submission histories are not combined.

The default remains one Task, one Whole Task Workflow, one branch, one worktree, and one pull request. Whole Task is an explicit Workflow scope, not an implicit or unnamed Task Slice. Task Slices are explicit rather than inferred from file changes or agent judgment. v1 requests creation with `awctl start TASK-ID --slice NAME`; this does not create a child Linear Issue or automatically decompose the Task. The complete Task Snapshot and stable slice name appear in Implementer and Reviewer Handoffs. The name is a user-declared, agent-visible scope label, not a separate stored slice specification or merely a technical branch suffix. AW does not mechanically prove compliance with the semantic boundary. A role stops for human clarification when the Task Snapshot plus label is genuinely unclear, and AW rejects ambiguous selection among sibling workspaces rather than guessing.

A Task may retain a Whole Task Workflow and one or more Named Slice Workflows at the same time, including when a Named Slice is added after a Whole Task Workflow was completed or submitted. A later Workflow captures the Task Source as it exists when that Workflow begins. It does not supersede, repartition, or reinterpret an earlier Workflow. AW does not attempt to prove that the scopes are non-overlapping; ordinary Git and review evidence reveal substantive overlap or conflict. Workflows with different scopes may execute concurrently in separate worktrees. AW does not serialize them merely because they share a Task, while duplicate Workflow admission for the same scope remains blocked under the current identity rules.

`awctl start` never silently reuses an existing worktree. If the same Task and Workflow Scope already has a retained Workflow, the command stops without mutating workflow state or launching an agent. It prominently reports the existing Workflow identifier, phase, worktree, uncommitted-change status, review status, and pull-request status, together with the applicable explicit continuation actions. The user may then resume or submit the existing Workflow or select another named scope. This protects unfinished or reviewed-but-unsubmitted work without automatically deciding what the user intended.

A changed Linear Issue does not relax this rule. To apply changed requirements to unfinished work, the user resumes the existing Workflow and explicitly adopts the newly captured Task Snapshot; AW then routes that Workflow back to implementation before review. If the existing Workflow already has a pull request, `start` still refuses to create or reopen the Whole Task Workflow. Continuing work in that same pull request is an explicit continuation of the existing Workflow. Starting another pull request for the Task requires an explicit named scope through `--slice`.

After GitHub confirms pull-request creation or adoption, AW stores Submission evidence containing the provider, repository identity, pull-request number and URL, head branch, Workflow identity, and scope. That record supports deterministic retries and status while the Workflow remains retained. GitHub remains authoritative for the request's mutable live status, which AW refreshes by the recorded repository and pull-request number when that status affects an operation.

v1 does not use retained AW history as a project-wide or cross-installation admission registry. Explicit cleanup may remove the Workflow, its audit history, and its Submission evidence. Starting a Workflow therefore checks whether its candidate branch already exists in relevant local Git state or as a live branch on the configured remote. An existing branch stops creation and directs the user to the existing work or to `--slice`; when neither branch exists, AW may proceed without searching historical pull requests. If cleanup or external branch deletion makes the name available again, starting the same Task and scope again is the user's responsibility. This deliberately accepts that two independent machines can race before either publishes shared Git state.

For a Linear-backed Task, the candidate branch identity uses the normalized Linear key directly and excludes the mutable Issue title. A Named Slice adds a normalized slice-name suffix to that key. The exact prefix and separator are naming-format details, but Whole Task and Named Slice formats must not create Git ref prefix conflicts. Repository context supplies the project boundary.

For a Markdown or pasted-text Task, AW generates a random 128-bit identifier when it captures the Task. A branch may also contain a normalized human-readable slug, but the slug is presentation metadata and never the identity. Before creating the Workflow, AW applies the same local and live-remote branch-existence checks; an actual identifier collision causes regeneration before any workflow state is created. Separate machines capturing the same text intentionally receive independent identifiers and Workflows. AW does not derive identity from a content hash because identical source text may legitimately be run more than once.

After creation, commands select a Workflow from the current managed worktree when the caller is inside that worktree. This is the ordinary short path for commands such as `awctl review`, `awctl pr`, and `awctl cleanup`. Outside a managed worktree, the caller supplies the immutable Workflow identifier explicitly, such as `awctl pr --workflow WORKFLOW-ID`; the dashboard uses the same identifier. AW does not guess from a Task identifier, slice name, branch-name prefix, or mutable title when selecting among existing Workflows. Missing, conflicting, or unprovable worktree metadata stops the command without mutation.

### 1.3 Planned Workflow Variants

A Task Slice must not be used to label competing implementations of the same Workflow Scope. A slice changes which part of the Task is in scope. A Workflow Variant instead identifies one candidate implementation among several deliberate attempts at the same Task Snapshot and scope, for example attempts produced with different models. Every Variant owns an independent branch, worktree, agent configuration, implementation/review loop, evidence, and lifecycle; the Task requirements remain the same.

Workflow Variant support is planned for v1 or early v2 and is not required by the Initial E2E Milestone. Until that support exists, duplicate Workflows for the same Task and scope remain rejected; users must not bypass the rule by inventing slice names for alternatives. The exact CLI surface, optional variant-specific guidance, comparison and winner-selection flow, submission policy, and cleanup of unselected candidates require a focused design decision before implementation.

## 2. Established execution model

Agentic Workflows combines two kinds of behavior:

- The **deterministic workflow** owns orchestration, authoritative state transitions, Git integration, policy enforcement, and verification.
- **Agent work** is non-deterministic. An agent performs a bounded role, such as implementation or review, inside the workspace prepared by the deterministic workflow.

The deterministic workflow is the glue. Agent output is input to that workflow; it is not authoritative merely because an agent reported success.

Conservative blocking must never create an operational dead end. Every blocked, invalidated, or interrupted operation preserves available work and evidence and offers a supported human recovery path without requiring database edits or a completely new Workflow.

The Initial E2E Operation Status set is exactly `Pending`, `Running`, `Completed`, `Failed`, and `Interrupted`. `Failed` and `Interrupted` are never terminal Workflow states or Workflow phases. A user-requested stop such as Ctrl+C and a positively confirmed vanished execution are both `Interrupted`, distinguished by typed reasons; AW does not add a `Canceled` Operation Status that could be confused with Linear Task cancellation. Review findings and other successful semantic outcomes belong to the Result Envelope rather than Operation Status. When an Operation fails or is interrupted, the Workflow retains its current phase, preserves available work and evidence, and exposes every applicable Attention Requirement and recovery action. Every retry or resume creates a new immutable Operation linked to the predecessor it follows; it never reopens or mutates the predecessor. A later successful Operation may supersede the failed attempt for current routing while the original record remains in history. Reusing an eligible agent session or starting another one is decided independently by session policy and any valid override. The Workflow ends further work only through an explicit user-controlled lifecycle decision such as abandonment or cleanup; exact command semantics remain a separate decision.

The Initial E2E Workflow Phase set is exactly `WorkspacePreparation`, `Implementation`, `Review`, and `Submission`. A clean review advances the Workflow to `Submission`; readiness is derived from current review and worktree evidence rather than represented as another phase. Submission is the umbrella for deterministic commit, push, and forge change-request creation or update. v1 implements a GitHub pull request through `awctl pr`; a later GitLab adapter may produce a merge request without making merge part of Submission. Successful PR creation records Submission Evidence while the Workflow remains retained and available to return to `Implementation` for additional work. Cleanup deletes the Workflow rather than transitioning it into a `CleanedUp` phase. After the applicable external teardown, one transaction deletes all of that Workflow's run-specific current state and history while preserving installation-level project/repository configuration and sibling Workflows. No pass, report, evidence, or event remains orphaned. The internal commit, push, and forge-request boundaries remain reusable if later usage justifies separate public commands.

The Initial E2E model has no single authoritative Workflow Status or Outcome enum. CLI and dashboard labels are projections of Workflow Phase, current Operation and Execution Observation, active Attention Requirements, explicit abandonment, clean-review eligibility, and Submission Evidence. A label such as `Submission · submitted` is therefore not a terminal stored state: the same retained Workflow can later return to `Implementation` for another reviewed batch. Projection fields may be returned by queries for convenience but cannot become an independently mutable source of truth.

Human-input gates are represented by typed Attention Requirements, not by adding Workflow phases. AW creates one only when safe continuation requires a human policy choice or manual/external action. Operation failure, interruption, or temporary unreachability already has Operation Status, diagnostics, and a Recovery Plan and does not automatically receive a duplicate attention record. The Initial E2E set contains only `TaskChangeDecision`, `PassContinuationDecision`, `PassBudgetContinuation`, `LinearCancellationDecision`, and `RepositoryReconciliation`. `PassContinuationDecision` is derived from a normally completed pass only when its Result Envelope identifies a concrete material decision or external prerequisite, explains why no safe in-scope continuation exists, and proposes a resolution. Routine findings, unrelated failures, and uncertainty the agent can investigate do not qualify. Session loss, result-contract failure, review staleness, provider failure, and temporary unreachability remain in their existing Operation, evidence, eligibility, and Recovery Plan concepts. A new attention reason requires a concrete end-to-end scenario that these concepts cannot represent without ambiguity. Attention Requirements are current derived alerts, not objects the user resolves individually. Every deterministic boundary and intended recovery action revalidates all available facts, exposes all requirements that still apply, and automatically clears every current projection that no longer applies. One ordinary action may clear several alerts. There is no `mark-resolved` command or requirement checklist; creation and clearance remain in the Workflow Audit Trail. The derived `AttentionRequired` gate blocks AW from starting the next gated action while any requirement applies, but does not automatically interrupt a running pass or convert completed work into failure. `awctl cleanup --force` remains the immediate discard path.

Simplicity is a functional constraint. The design should expose only the distinctions needed by observed workflows, keep ordinary execution explainable, and treat proliferating states, flags, override scopes, or special recovery procedures as a reason to pause development and simplify the model. Extension points may be preserved without implementing speculative flexibility.

### 2.1 Agent participation

Two agent roles currently operate inside an Agentic Workflows-managed execution:

- the implementation role changes files;
- the review role assesses the implementation independently.

An agent execution is a Managed Agent Pass only when AW starts and tracks it with a recorded Handoff, role, session, lifecycle, and result. A human may instead open an agent independently in the retained worktree. That activity is Unmanaged Work: AW does not log the agent attempt or show it as a workflow pass, although it reconciles the resulting file and Git state at later deterministic checkpoints.

An External Orchestrator may supervise the broader process but is not currently a managed role inside Agentic Workflows. In the product owner's present topology, this is the ChatGPT/Codex application and its agents or chat running on a Windows machine, separate from the VPS where Agentic Workflows and its execution sessions run. Use **External Orchestrator** for that environment and **AW control plane** for the deterministic product authority; do not use “orchestrator” alone for both.

Execution reachability is not Operation outcome. If Herdr becomes unreachable after an agent was confirmed running, AW retains the timestamped last confirmed observation and shows current reachability as unavailable. It does not infer Failed, stopped, or Interrupted. A possibly active Implementer blocks another pass because it may still change files. A possibly active Reviewer does not block the next pass, but the earlier review permanently loses authority to produce current clean-review evidence once another pass starts. Read-only inspection and `awctl cleanup --force` remain available. Interrupted is recorded only after reconciliation positively establishes that the original execution disappeared without a valid Result Envelope. If Forced Cleanup cannot confirm teardown, its structured partial result supplies the information needed to handle possible orphaned AW-owned Herdr resources directly after AW deletes the Workflow state; unrelated Unmanaged Herdr Resources remain untouched.

### 2.2 Role, session, harness, model, and mode

Role and execution selection are separate concepts. The current defaults are policy choices that may change when research or operating evidence shows a better approach:

- Implementation fixes normally resume the original implementation session so it retains its task and code context.
- The initial formal review starts in a separate session without implementation conversation history.
- A later re-review may resume the same review session.
- Implementation and review have separately configurable harness, model, mode, and session-reuse defaults.
- The configured session-reuse policy determines whether a later pass normally starts a new session or resumes an eligible earlier session.
- The user may override session reuse for the next applicable role pass only. Once that pass starts, later passes return to the configured policy.
- Selecting a different model changes the workflow's model selection for that role and applies to all of its later passes until changed or cleared. Implementer and Reviewer model selections are independent.
- A harness selection will provisionally have the same role-scoped lifetime as a model selection, subject to later usage evidence. The lifetime of mode changes is deferred.
- If the expected session cannot be verified or resumed, Agentic Workflows stops for a user decision instead of silently launching a replacement.
- A new implementation session receives a complete bootstrap handoff, including the full task snapshot.

An Agent Session may exist without a Managed Agent Pass currently executing in it. The retained Implementer and Reviewer sessions may therefore coexist while their passes normally alternate through implementation, review, repair, and re-review. A proven idle session does not block another eligible pass. An executing or uncertain Implementer does block another pass because it may still mutate files. An executing or uncertain Reviewer is read-only by contract and does not hold that mutation gate, but starting another pass permanently disqualifies the earlier Review Pass from supplying current clean-review evidence. Deliberately aggregating several concurrent reviews remains deferred.

The architecture keeps role and session allocation independent so future policy may permit one session to fill both implementation and review roles if evidence supports that choice. This is not the current formal-review default.

The user may make or replace a Next-pass Session Override while the current agent pass is running. This is a future-intent change only: it selects session reuse for the next pass of a role but cannot change the current pass, Handoff, Task Snapshot, or worktree permissions. AW resolves the latest applicable override at the handoff boundary, revalidates it, and consumes it when the selected pass starts. Thus, while an Implementer is active, the user can choose whether the next review should use the previous Reviewer or a new Reviewer without interrupting implementation.

## 3. Git-backed implementation and review loop

The agreed high-level sequence is:

1. The deterministic workflow prepares a Git worktree at a known baseline.
2. An Implementer performs an implementation pass by editing files in that worktree.
3. The implementation pass leaves uncommitted worktree changes. The Implementer does not create a Git commit.
4. A Reviewer reviews the uncommitted worktree diff.
5. If the Review Pass returns findings, the deterministic workflow hands the findings and the same uncommitted worktree changes back to the Implementer for another pass.
6. Implementation and review repeat until the review succeeds or another workflow outcome ends the loop.
7. After successful review, AW stores the Review Report and the identity of the exact reviewed uncommitted state in durable workflow data, then enters a submission-ready state without committing.
8. The user may inspect the retained worktree and Review Report directly or with an external agent that is not part of the managed workflow.
9. The normal `awctl pr` wrapper verifies the worktree, creates a commit, pushes it, and creates or updates the pull request or merge request by composing three internal deterministic actions.
10. Optional PR-on-clean automation may invoke the same deterministic operation later; manual PR creation is the default.

Every automatically started Implementation Pass or Review Pass consumes one unit from the current Managed Agent Pass Budget. The default budget is six: the initial Implementation Pass and Review Pass, followed when necessary by two repair-and-review pairs. A finite budget is checked at pass boundaries: AW lets an active pass finish and records its result, but pauses before starting another Managed Agent Pass when none remain. The workflow requires human interaction rather than becoming Failed. Status includes the completed and remaining pass counts and the best available token and cost measurements. The user can explicitly continue with a new budget.

The budget may instead be set explicitly to Unlimited. In that mode, pass count never causes a pause, allowing intentional unattended execution. Unlimited does not suppress other stops and must be represented as a deliberate policy value rather than inferred from missing or invalid configuration. When a finite budget is exhausted, `awctl continue` starts a new automatic batch with the currently configured budget, which is six by default. `awctl continue --max-passes N` sets the size of that new batch, and `awctl continue --max-passes unlimited` makes that batch unlimited. These invocation-scoped values do not silently rewrite the saved configuration. A possible elapsed-agent-time budget is reserved but not specified. Provider usage-window detection, the meaning of provider exhaustion, and automatic recovery after a reset are intentionally deferred.

Task requests to commit, push, or create a pull or merge request do not create a conflict after implementation. They describe the desired result, while AW assigns those mechanics to the deterministic actions coordinated by `awctl pr`. AW-managed Implementers and Reviewers do not create commits as part of their Managed Agent Passes. This rule does not prevent a human or an independently opened agent from using Git outside the managed workflow.

Like the prototype, v1 exposes only `awctl pr`; commit, push, and forge submission are internal deterministic actions. The wrapper and its actions are durably resumable and idempotent across the chain. Continuing a partially completed submission means running `awctl pr` again, not invoking a separate PR retry or resume command. The new invocation reconciles real local and remote state before acting, reuses the exact commit already created for the action chain, does not push it again when the intended remote branch already contains it, and does not create a duplicate when the correlated pull or merge request already exists. It creates a new immutable Operation linked to the earlier attempt while retaining the same frozen PR Intent. If AW cannot prove that an observed effect belongs to the same action chain and target, it stops with a Recovery Plan rather than guessing or replaying everything.

For a Linear-backed Task, the generated pull-request body includes a deterministic closing reference such as `Fixes DEV-123`. This explicitly establishes the linkage required for GitHub–Linear merge automation and applies to every Whole Task or Named Slice pull request for that Task. v1 keeps the reference even though the branch name already contains the Issue key. Removing it requires a later explicit decision supported by evidence that branch-based auto-linking alone is reliable; dogfooding does not change the rule automatically.

A Linear-backed submission also requires exactly one Primary Publication Category: `Feature`, `Bug`, `Chore`, `Docs`, or `Refactor`, mapping to `feat`, `fix`, `chore`, `docs`, or `refactor`. `Research` may coexist as an orthogonal modifier and unrelated labels are ignored for type selection; for example, `Feature` plus `Research` still produces `feat`. No primary category or several primary categories stops submission before Git or GitHub mutation. AW reads classification from controlled Linear labels and never replaces unrelated labels as a side effect of publication.

A clean Reviewer returns public-safe Reviewed Publication Metadata for the exact Review Target: an action summary, description, and validation statement. The summary is a concise one-line lower-case action phrase without its own type, Task suffix, or sentence punctuation and must leave the complete subject within 72 characters. Description and validation are each at most 2,000 characters, contain no headings, and exclude private Task instructions, credentials, local paths, and conversation content. AW does not fall back to the mutable Linear Task title when these fields are missing, invalid, or stale.

Deterministic submission constructs the commit subject and PR title as `<type>: <reviewed action summary> (<TASK-ID>)`. An AW-created commit adds `Task-Review: <pass-id>` as a trailer. The PR body contains `Summary`, `Tracking`, and `Validation` sections. Tracking contains both the canonical Linear link and the deterministic `Fixes TASK-ID` reference; Validation ends by stating that independent review accepted the exact change. The completed title, body, and commit message are frozen in the PR Intent and reused across retries. The metadata source for a forced submission without clean reviewed metadata remains to be specified with the rest of the forced-submission contract; no Task-title fallback is implied.

Before any mutating action, `awctl pr` performs one deterministic preflight. Normal preflight requires a current clean Review Report, materializes the current proposed tree and verifies it against the Reviewed Tree, uses a Worktree Fingerprint when changes are uncommitted, verifies repository, branch, base, remote, and forge target identity, and stores a frozen PR Intent for that exact content and action chain. No commit, push, or forge write starts before the intent is durable.

`awctl pr --force` bypasses only the current clean-review requirement. It still freezes the exact current worktree content and performs all target, revision, concurrency, and destructive-scope checks. Neither normal retry nor forced retry may silently replace the frozen content with later worktree changes.

The explicit `--force` flag is sufficient human confirmation. AW records and displays the bypass but does not require an interactive confirmation, a typed phrase, or a second flag. Because the operation targets an isolated task branch and worktree and never force-pushes or rewrites the shared base, an erroneous forced submission is recoverable.

Force is invocation-scoped only. It cannot be persisted as configuration at any level, inherited by a later `awctl pr` invocation that omits `--force`, or enabled for automatic PR-on-clean behavior. Each bypass requires an explicit `awctl pr --force` invocation.

The internal boundaries must be reusable so separate public `awctl commit` or `awctl push` commands can be added later if usage justifies them. v1 does not expose those commands merely to anticipate possible flexibility.

Remote branch divergence stops only the unsafe submission operation. AW never overwrites, resets, force-pushes, or automatically pulls, merges, or rebases an unexpectedly changed remote branch. It reports the expected and observed revisions and tells the user to fetch and reconcile the remote changes manually. The worktree and unrelated safe commands remain available. The user then reruns `awctl pr`, which revalidates and resumes the correlated action chain when safe. No separate mark-resolved command, recovery comment, or workflow-state repair is required. The `--force` option bypasses review policy only and cannot bypass remote-revision checks or enable Git force-push behavior.

After a pull or merge request exists, the worktree and branch may be retained for human-directed follow-up. Another implementation/review cycle followed by `awctl pr` may produce a later commit, push it to the same branch, and update the existing request. The one-commit rule applies to one submitted batch after any number of implementation/review passes; it does not impose one commit on the lifetime of the request.

The user may also perform follow-up work directly or through an external agent. AW does not manufacture history for that Unmanaged Work. It detects its observable effects at the next checkpoint, treats earlier dependent review evidence as stale, and requires either fresh applicable review evidence or an explicit Force Override before policy-dependent submission.

A fresh Review Pass may assess a local commit created through Unmanaged Work. AW binds the Review Report to the comparison baseline content and complete Reviewed Tree without claiming that AW created the commit. If a human or external agent merely commits an already reviewed tree, the changed commit SHA does not invalidate the content review. `awctl pr` may adopt a clean local `HEAD` whose complete tree equals the Reviewed Tree, treat the internal commit action as already satisfied, and continue with push and forge submission after separate ancestry and target checks. Any later content or mode change invalidates the review evidence. Without a clean review, submission still requires an invocation-scoped Force Override.

### 3.1 Implementation-to-review and review-to-implementation handoffs

Agentic Workflows constructs every handoff deterministically from authoritative durable workflow data. Agents do not pass authoritative task context directly to one another.

Every full or bootstrap Handoff uses one explicit three-layer order:

- **Workflow Instructions** are AW-owned lifecycle, safety, and role directions prepended before the Task Snapshot.
- The **Task Snapshot** is the immutable source-derived statement of the required outcome and context for the pass.
- The **Pass Brief** is AW-generated direction for the bounded pass, such as implementing without committing, reviewing without editing, addressing a specific findings batch, or returning a structured result. It is recorded with the pass and may vary without changing the Task Snapshot, but it must not silently change the Task requirements.

The prototype demonstrates all three concerns but does not compose them uniformly. Its review and integration handoffs begin with authoritative workflow instructions and place Linear requirements later, initial implementation places the Linear Issue before workflow-owned implementation instructions, and automated implementation passes append findings and result-delivery directions. The new design should make these layers explicit rather than inherit that incidental ordering.

Workflow Instructions govern AW lifecycle, safety, Git ownership, and role boundaries. The Task Snapshot governs the requested outcome. A Pass Brief may select or narrow the current step but must not redefine that outcome. Repository Guidance follows the status convention in `architecture.md`: Product Invariants are binding, Design Directions may be coherently refined, and Open Areas permit reversible local choices. The system does not ask agents to search broadly for textual contradictions.

The Handoff must preserve Implementation Latitude. It supplies required outcomes, constraints, applicable findings, evidence, and the result contract, but does not prescribe a mechanical edit sequence unless that sequence is itself an explicit requirement. A cohesive task may span several components when reasoning across them produces a better design. Deterministic orchestration bounds and observes Agent Work; it does not replace the Implementer's technical judgment with an unnecessarily detailed plan or force an ad hoc workaround to satisfy a Design Direction literally.

Applicable Repository Guidance constrains the implementation without expanding the Task Snapshot. An architecture document is not a backlog that the Implementer may implement opportunistically. A Task Snapshot conflict with a Product Invariant is blocking and the pass reports the exact conflict. A Design Direction may be refined when a coherent solution preserves the task and invariants; the result reports that choice and its rationale. An Open Area blocks only when proceeding would silently decide a material product question. AW's harness integration must ensure the guidance is available to the pass even when the selected harness does not automatically discover `AGENTS.md`; the pass record identifies the guidance paths and repository revision used.

- A new Reviewer receives the Task Snapshot, current worktree state or Review Target, available Validation Evidence, and the implementation result needed for review.
- When findings return to the original implementation session, Agentic Workflows may send an incremental handoff because that verified session already received the task snapshot.
- When work moves to a new implementation session, Agentic Workflows sends a bootstrap handoff containing the task snapshot, current workspace state, and applicable unresolved findings.
- Agent-provided summaries may supplement a handoff but never replace the authoritative task snapshot, workspace facts, findings, or validation evidence.
- Agentic Workflows decides which role and session should run and requests the action through its Herdr gateway. Herdr owns the actual session start or resume and instruction delivery.

The initial Herdr gateway speaks in AW workflow operations rather than exposing Herdr's full command set. Its bounded responsibilities are target capability inspection, Workflow workspace preparation or inspection, starting or resuming one Managed Agent Pass, observing or interrupting its correlated execution, retrieving its correlated output and result transport, and tearing down resources owned by a resolved Workflow. Stable target, workspace, session, execution, and AW Operation identifiers support reconciliation across that boundary. A CLI-backed adapter performs the Herdr-specific command composition; neither domain nor application code receives a generic command-execution escape hatch.

Workspace preparation is an idempotent request for one immutable Workflow identity and its resolved repository, base, branch intent, and requested managed location. Herdr may create the intended Workflow Workspace or return the one already proven to belong to that same Workflow. The result includes the stable target and workspace identifiers, canonical path, and observed ownership facts needed for AW to persist and later revalidate the association. Retrying after a timeout or uncertain response reconciles this identity and must not create another worktree.

If ownership evidence is absent, duplicated, contradictory, or belongs to another Workflow, preparation stops before agent launch and preserves every observed workspace. AW neither guesses which worktree is intended nor silently adopts, deletes, or repairs one. Its Recovery Plan provides one supported command for complete AW-side recovery, without database inspection or manual state edits. For the retained Workflow, `awctl cleanup --force` clears the AW-owned records and asks Herdr to tear down only resources whose ownership and managed boundaries are proven; unproven or unrelated workspaces remain untouched and appear in the structured result.

Before Herdr is asked to launch or resume an agent, AW durably assigns the Managed Agent Pass and its launch request to the immutable Operation identity. If the response is lost, AW reconciles that exact identity. A proven running execution is reattached and observed; a proven idle session is available for a later eligible pass; and a request proven never to have started may follow the ordinary recovery path. While an Implementer execution remains uncertain, AW does not start another pass in that Workflow Workspace. An uncertain Reviewer does not block the next pass, but once another pass starts, that Review Pass is permanently ineligible to produce current clean-review evidence and any late result is retained only in history.

Herdr retains or exposes the completed pass output and Result Envelope under that Operation identity until AW acknowledges durable ingestion. AW sends or records that acknowledgement only after the SQLite transaction containing the validated immutable envelope, typed projection, resulting events, and new current state commits. If AW restarts or reconnects first, it retrieves and validates the same result rather than rerunning the pass merely because it missed completion.

The gateway may observe Herdr resources outside AW's control, including user-created or externally managed panes, sessions, processes, workspaces, and worktrees. It correlates and mutates only resources with stable ownership facts for the exact Workflow and Operation. Names, paths, repositories, branches, or neighboring panes are insufficient by themselves. Missing, duplicate, or contradictory ownership produces a Recovery Plan and leaves every unproven resource untouched.

Target inspection returns a structured compatibility-and-capabilities response. Before a mutating request, AW verifies only the named capabilities mandatory for that request. If one is absent, AW records a precise failed Operation and Recovery Plan without disabling other supported operations on the target; for example, missing correlated-result support may prevent a Managed Agent Pass while workspace inspection or cleanup remains usable. Compatibility follows the structured contract and required capabilities rather than an exact Herdr-version allowlist. Cache and wire-format details remain inside the adapter unless they become observable workflow correctness concerns.

Change detection for re-readable Task Sources, currently Linear and Markdown files, aligns with handoff boundaries. Optional periodic detection may inform the user during a long-running phase, but it does not automatically interrupt that phase. The exact warning mechanism remains open.

### 3.2 Base-conflict integration

AW retains the prototype's explicit `awctl integrate` command for one narrow case: an unpublished clean-reviewed result must be replayed onto an advanced base, and deterministic replay produces file conflicts. This is separate from an external agent creating a commit in the existing task worktree. A local commit changes Git history identity but, when it preserves the same Reviewed Tree, does not change the Review Target or create a merge conflict merely by existing in that worktree.

`awctl pr` reports a detected base conflict and stops the unsafe submission action; it never launches conflict-resolution work automatically. When the user explicitly runs `awctl integrate`, AW revalidates the task, repository, base, review, and publication state and reproduces the conflict in an isolated checkout. A bounded managed agent pass may resolve and validate files there, but AW retains exclusive ownership of staging, history construction, installation, push, and forge actions.

AW proves the isolated file result before installing it into the task branch through deterministic Git actions. Successful installation invalidates the old Review Report and requires a fresh independent Review Pass. `awctl integrate` never publishes. A conflict-free recheck sends the user back to `awctl pr` without launching an agent. v1 should preserve these safety properties while avoiding the prototype's highly specialized recovery states unless concrete failures require them.

## 4. Review Target and Worktree Fingerprint checkpoints

The Reviewer assesses one exact Review Target. AW identifies it by the comparison baseline content and the complete proposed Reviewed Tree. Their canonical content identities are Git tree identities qualified by the repository's object format, not an AW-specific per-file hash document. A point-in-time Worktree Fingerprint helps construct and verify the proposed tree when changes are uncommitted; neither the current commit SHA nor a continuously running filesystem watcher defines review validity. In the ordinary managed path, AW builds that tree through a private temporary index that does not alter or depend on the user's real staging state. When Unmanaged Work has already committed the files, AW obtains the same proposed tree from clean `HEAD`.

The fingerprint covers the uncommitted change set inside the managed worktree relative to the workflow baseline:

- the path and change kind for every modified or deleted tracked file and every non-ignored untracked file;
- the content hash and relevant Git mode for each path that has content;
- the workflow baseline needed to interpret the change set.

Timestamps, staging versus unstaging of identical worktree content, ignored files, caches, and build output do not affect the fingerprint. They cannot change the content AW's normal PR operation is intended to commit.

AW recalculates the fingerprint only at deterministic boundaries that need it:

1. After the Implementer finishes, or after AW observes user-selected Unmanaged Work, and immediately before the review handoff.
2. After the Reviewer finishes. The baseline content and proposed tree must equal their pre-review values. AW also verifies that `HEAD`, the index, and worktree did not move during the pass so Reviewer mutation or concurrent interference invalidates that pass.
3. When recording a clean Review Report, which stores the accepted Review Target.
4. Immediately before `awctl pr`, which must match the accepted Review Target unless the user supplies `--force`.

These checks are source-agnostic. A mismatch invalidates the review evidence whether the files changed because the Reviewer violated its read-only contract, an Implementer began another pass, a human edited the worktree, or an external agent worked there. The Reviewer Operation and any late Result Envelope remain represented in the Workflow Audit Trail with the invalidation reason, but they cannot yield a current clean Review Report or authorize automatic routing. AW presents the condition as a notification with ordinary choices rather than a special repair workflow: review the current target again, continue working, retain the Workflow, or invoke `awctl pr --force`. Without force, PR creation rejects the missing or stale clean-review evidence.

Every later implementation repair that changes the proposed tree requires a new Review Pass. Staging, unstaging, or committing the identical tree does not change the reviewed content. The race-free capture procedure, deterministic commit construction or adoption, and recovery behavior when a stable fingerprint cannot be established remain to be specified.

The prototype supplies a behavioral reference: it creates a content-based snapshot covering the baseline, HEAD, branch, index state, Git status, tracked files, non-ignored untracked files, modes, symlinks, and supported submodule state. It reads twice to reject a capture that changes during observation. During `pr`, it stages through a private temporary index, verifies that the resulting Git tree represents the reviewed bytes and modes, and refuses publication when the evidence differs. The new implementation uses that Git-native tree approach; its concrete command sequence remains Implementation Latitude but must preserve equivalent guarantees.

Both normal and forced PR creation require that no managed agent pass is active in the workspace. The deterministic PR operation holds the exclusive workspace mutation lock through verification, commit construction, push, and pull-request creation. Read-only commands, Next-pass Session Overrides, and Role Model Selections may still execute during an active agent pass because they do not mutate the active pass or worktree.

## 5. Validation evidence and routing

Prototype research is recorded in [docs/research/prototype-validation.md](docs/research/prototype-validation.md). It confirms that focused test selection and execution are agent-driven prompt behavior. The deterministic controller validates structured check evidence and chooses workflow routing; it does not select or execute the commands itself. TDD is optional, Reviewer validation defaults to focused-first, and linting is merely an agent-selected check unless a repository or task explicitly requires it.

The prototype rejects an Implementer completion containing any failed check. Even when the same failure is reproduced on the unchanged base and diagnosed as unrelated, the Implementer must report blocked, the loop escalates, and no Reviewer starts automatically. This is a known friction point rather than an inherited requirement.

The successor preserves every unresolved observed failed check as failed evidence but routes independently. A failing command does not interrupt an Implementation Pass: it causes the Implementer to investigate, fix the implementation or test when the proposed change caused the failure, and rerun the relevant Focused Validation before reporting the work ready for review. Intermediate red/green TDD steps are internal agent work rather than AW state transitions. If the Implementer concludes that a remaining failure is pre-existing or otherwise unrelated to the Task, the Result Envelope records that classification and its supporting evidence. The Implementer does not modify unrelated tests or functionality merely to clear the failure; repairing unrelated behavior requires existing Task scope or later explicit authorization. AW creates a prominent non-blocking warning for the user and, when the requested work is otherwise complete and no human decision is required, automatically starts the Reviewer without waiting for the user to acknowledge the warning. This non-blocking route supports unattended batches of Workflows rather than turning every warning into a manual overnight stop.

The Reviewer receives the warning and all available Validation Evidence and independently checks whether the failure is related. A related failure or unsupported unrelatedness claim may support findings and another implementation pass. An unrelated or deliberately deferred limitation may remain visible alongside a clean Review Report and through submission reporting; clean review means the Reviewer found no actionable defect in the Review Target, not that every possible check passed. That clean Review Report is ordinary current clean-review evidence: normal `awctl pr` accepts it without another acknowledgement or `--force`, while its reviewed validation statement discloses the limitation. AW never changes a recorded failure into a pass or implies that an unrun check succeeded. Initial E2E always continues on a warning when no independent gate applies. A possible later global stop-on-warning policy would pause AW after accepting the same truthful result; it would not turn the warning into an agent-authored failure or change the pass's semantic outcome.

Broad Validation is user-scheduled by default. A suite containing thousands of tests may run manually, in CI, nightly, or at another chosen boundary without blocking ordinary implementation, review, or `awctl pr` merely because it has not run. The workflow records its known status and limitations. It does not automatically launch the full suite.

AW must not infer that an agent-selected command actually ran merely from a structured claim, and it must not add a deterministic test-selection engine, universal linter, or new protection mechanism without a demonstrated workflow need. In v1, linting and type checking use the same agent-selected Validation Evidence model as tests. They are not separate deterministic stages and do not receive stricter routing merely because of their check type.

A later milestone may add project-configured commands as a deterministic validation pipeline after the final Review Pass. This is a reserved extension seam rather than a v1 plugin framework. The command configuration, failure routing, and effect on review freshness require a separate decision before implementation.

### 5.1 Workflow audit trail

Every Managed Agent Pass and deterministic AW action appends its known inputs, effective execution configuration, lifecycle events, detailed structured report, evidence, measurements, warnings, decisions, overrides, and state transitions to the Workflow Audit Trail. Later events may supersede an earlier conclusion, but ordinary commands and recovery actions never rewrite history to make the earlier event disappear. AW does not store every agent message, terminal interaction, or tool call. The dashboard and `awctl` read the same durable record.

Each structured pass report must be detailed enough to explain what the role attempted, what changed or was assessed, what evidence supports the result, what remains uncertain, and what the next role or External Orchestrator needs to know without reopening the original agent conversation. The same durable result supports deterministic routing, dashboard summaries, expanded human inspection, later Handoffs, and portable reporting. AW composes these reports with deterministic history and current state into a Workflow Report whose intended consumer is often an external planning agent or chat rather than a human reading every field directly. Raw transcripts, hidden reasoning, terminal interaction, and individual tool calls remain outside this contract.

An agent delivers its pass report as exactly one UTF-8 JSON Result Envelope in an AW-authorized location outside the worktree. The envelope is correlated to the expected pass and validated against one versioned universal schema before AW accepts its outcome or performs another handoff. A role discriminator selects a role-specific payload and validation rules; implementation and review therefore share one envelope contract without turning role-specific fields into a loose collection of optionals. Detailed Markdown-capable narrative fields live inside the same envelope as the machine-significant outcomes, findings, resolutions, checks, and correlation data; no separately editable pass-report document may become a second source of truth. Implementer outcomes are exactly `ReadyForReview` and `DecisionRequired`; Reviewer outcomes are exactly `Clean`, `ChangesRequired`, and `DecisionRequired`. `ChangesRequired` requires actionable findings and `Clean` forbids them. `DecisionRequired` must include the concrete unresolved matter, why automatic continuation is unsafe, and its proposed resolution. Warnings remain orthogonal evidence and never become another outcome. Agents do not report `Blocked` or `Failed`; those words remain control-plane and diagnostic concepts. Missing, malformed, duplicate-key, mismatched, or internally inconsistent envelopes fail validation and cannot authorize a successful transition.

Every role-specific payload requires a concise summary, a detailed Markdown-capable account of the work or assessment, structured Validation Evidence, and structured warnings, limitations, and unresolved risks. An Implementer payload also contains completed work and one resolution for every finding supplied in its Handoff. A Reviewer payload also contains actionable findings and, when `Clean`, the reviewed public action summary, description, and validation statement. A `DecisionRequired` payload adds the unresolved matter, why safe continuation is unavailable, and the proposed resolution. AW derives changed files, Review Target, Worktree Fingerprint, and other repository facts independently; an agent description cannot override those facts. The schema may choose clear property names and nesting during implementation, but it must enforce these required meanings and their role- and outcome-specific consistency rules.

Before parsing or ingestion, AW enforces a 1 MiB (1,048,576-byte) limit on the complete UTF-8 Result Envelope. An oversized result is invalid and produces the same precise recoverable result-contract failure as another invalid envelope; AW does not truncate it or route from a partial result. Raw transcripts, complete diffs, terminal logs, tool-call histories, and binary artifacts are not envelope content and are not copied into SQLite. A bounded evidence summary and stable external reference may identify large evidence retained by its owning system or artifact store.

Every envelope declares its schema version. Pre-stable AW accepts and reads only the version shipped with the installed build; new Handoffs always request that version. Rapid-development upgrades may deliberately break retained envelopes and projections, and v1 development does not carry legacy readers or automatically rewrite historical JSON. AW detects an incompatible version and refuses to interpret it. Backward-compatible history and forward migrations are deferred until a later stabilization decision rather than constraining the next month of schema development.

If Herdr positively confirms that the agent turn completed normally but the Result Envelope is missing or invalid, AW records the Operation as Failed with a precise result-contract diagnostic. It does not call the Operation Interrupted, because execution completion is known. The worktree, session, delivery artifact when present, and all other evidence remain available through the ordinary Recovery Plan.

The JSON file is a temporary cross-process delivery mechanism. It remains recoverable by the expected Operation identity until AW acknowledges durable ingestion. After successful validation, AW persists the complete immutable Result Envelope and a typed relational projection of its query- and routing-relevant fields together with resulting workflow events, next current state, and any pending next-operation intent in one SQLite transaction. The envelope and projection are created from the same validated object and cannot be edited independently. AW acknowledges ingestion only after that transaction commits; a restart or disconnect before acknowledgement retrieves the same correlated result again safely. Later workflow decisions and dashboard reporting do not depend on the temporary file remaining present after acknowledgement. Git, Herdr, and artifact stores remain external sources of their own state and are referenced and reconciled rather than copied wholesale into the workflow database.

The v1 Workflow Report does not embed the complete code diff. It includes a compact changed-file list derived deterministically from the exact Review Target, not trusted from an agent-authored summary. Optional diff export is deferred until usage demonstrates a need.

The dashboard presents a concise projection of this information: workflow state; implementation, review, and handoff counts; the latest or final review verdict; a short outcome; and whether escalation or human interaction is required. Detailed reports remain available for inspection and copying without dominating the primary view.

The workflow-history query presents durable activity as an ordered sequence of meaningful steps rather than only the latest status. Each step includes a monotonically increasing workflow-local position, step type, applicable role and pass identity, timestamp, semantic outcome, short result, attention requirement, and references to its detailed report and evidence. The position is assigned atomically with the event and is the authoritative order within that Workflow; timestamps are informational. Implementer and Reviewer steps are independently expandable. Later events may supersede a conclusion but do not remove its earlier step from the timeline. Live dashboard notifications are freshness hints only; the API's persisted history remains authoritative. Cross-Workflow views may use recorded time and a stable tie-breaker for deterministic display, but that presentation order does not assert causality between independent Workflows.

Presentation status must distinguish **Failed** from **Changes required**. Failed means the pass or its execution failed. Changes required means a Reviewer completed its role and returned actionable findings for another Implementation Pass. Required human interaction is a third condition and must not be conflated with either failure or routine findings.

At any point, AW can return one step's report, compose selected steps, or compose the complete portable Workflow Report deterministically from durable records. These are query projections rather than additional stored report variants. The report includes all agreed structured context but not raw transcripts, individual tool calls, hidden reasoning, or the complete code diff.

Unmanaged Work is not retroactively represented as a managed pass. AW records only the externally observed state change, the time and checkpoint at which it was detected, its effect on existing evidence, and the resulting user options. This visible provenance gap is acceptable in v1. AW does not prevent experienced users from working outside the managed workflow; possible organization-level enforcement is deferred as a separate policy capability.

## 6. Human recovery contract

Every blocked, invalidated, or interrupted operation stores a durable Recovery Plan. It identifies the blocker, preserved work and evidence, retry safety, currently valid recovery actions, the exact `awctl` command for each action, and the effect or bypass involved. `awctl status` and the dashboard display the same plan, and every selected action revalidates current state before mutating anything.

Initial E2E keeps up to seven verified daily SQLite backups created with SQLite's consistent backup mechanism, separately from backups archived before an incompatible-schema reset. If AW detects database corruption, it preserves the damaged database and stops normal mutation. It presents one explicit restore command for a selected verified backup rather than repairing in place or silently choosing an older state. An explicit restore is followed by ordinary startup reconciliation against Herdr and workspace facts. This is a provisional same-machine recovery policy for corruption and operator mistakes; off-machine disaster recovery and a longer-term backup cadence and retention policy remain deferred.

The recovery surface should remain small and composable. v1 does not expose a generic `awctl retry` command. Repeating an idempotent deterministic action means rerunning its ordinary command, which reconciles the prior Operation before continuing. `awctl resume` is reserved for continuing an Abandoned Workflow or an interrupted Managed Agent Pass from preserved work. Other recovery actions include inspect/status, selecting an eligible agent/session for another pass, obtaining a new review, explicit force, and retain or stop. A generic retry command may be reconsidered after usage evidence, but AW must not grow a separate bespoke repair workflow for each error or require manual database edits.

Abandonment is an explicit, resumable stop to automatic routing. It retains the Workflow's managed worktree, sessions, evidence, reports, history, and durable current state. `awctl resume` is explicit authorization to continue. It revalidates current facts and immediately starts the single unambiguous safe next action when no Attention Requirement remains. If a requirement is active or materially different continuations require a user choice, the same command stops with the applicable Recovery Plan instead of guessing. Abandonment is neither failure nor cleanup.

Ordinary cleanup may refuse when unresolved Attention Requirements or another cleanup-policy gate makes deletion unsafe or ambiguous. `awctl cleanup --force` is not a stricter ordinary cleanup; it is an invocation-scoped destructive escape hatch. After resolving the exact Workflow and verifying its managed-target boundaries, AW asks Herdr for one bounded best-effort forced teardown of every process, pane, session, and worktree owned by that Workflow. Herdr may escalate from graceful interruption to forced termination of the owned process tree before removing the worktree with its required local Git bookkeeping. Open, idle, running, failed, unreachable, and uncertain execution states affect the reported component outcomes but never prevent the attempt.

After that attempt returns or times out, AW always deletes every piece of local AW-owned state for the selected Workflow. A completely confirmed teardown returns success. Any failed or unconfirmed external component produces a structured partial-cleanup result with a distinct non-zero exit code, last-known Herdr target, managed path, component outcomes, and manual-cleanup instructions. The exit code is returned after deletion and cannot become another gate or rollback. Because AW state is gone, the command is not retryable as a Workflow operation. Force never bypasses Workflow identity, resolved-path, or managed-directory safety checks, never affects sibling Workflows, and cannot be persisted as configuration.

Cleanup performs no remote Git, forge, or Linear mutation. It does not delete branches, rewrite history, push, or close or delete pull requests. AW itself invokes no `git` command as part of cleanup. AW requests session and managed-worktree teardown through Herdr, which owns the workspace and may perform the local Git worktree bookkeeping required to remove it safely. Ordinary cleanup deletes AW state only after the teardown result is durably known.

If Herdr cannot complete or confirm forced teardown, a managed process or workspace may remain orphaned; AW reports that uncertainty rather than claiming success. AW retains no Workflow-specific orphan record, tombstone, cleanup receipt, audit history, or other durable state afterward. Ordinary infrastructure logs follow the general logging policy and are not part of Workflow recovery. This does not expand cleanup into project-history, reference, remote, forge, or task-state management.

Recovery never edits historical records to make a blocker disappear. A retry or resume records a new immutable Operation linked to its predecessor, even when it resumes the same eligible agent session. A successful ordinary action records a new checkpoint and new evidence that supersede the blocked decision for subsequent workflow progress while preserving the blocker and stale evidence in history. For example, another Implementation Pass and clean Review Pass can make the current worktree eligible for normal PR creation without changing the earlier invalid Review Pass into a valid one.

Humans and external agents remain free to inspect or change retained worktrees. AW detects resulting evidence drift at the next deterministic checkpoint, warns the user, and blocks only operations that would rely on stale evidence. It preserves the current worktree and never silently rolls external changes back.

The dashboard and audit history must remain truthful about provenance. They may record that externally caused file or Git state appeared and how AW responded, but they must not represent an external agent attempt as a Managed Agent Pass or imply that its unavailable conversation and actions were captured.

Herdr is not dedicated to AW. User-created and externally managed panes, sessions, processes, workspaces, and worktrees are Unmanaged Herdr Resources. Reconciliation may observe them but never adopts, resumes, interrupts, or deletes them without proven Workflow ownership. A collision or ambiguous correlation stops only the affected AW action, preserves the external resource, and presents ordinary recovery choices; it never turns broad Herdr inspection into cleanup authority.

## 7. Open details

The next questions cover:

- the configuration scope of Workflow Instructions and the composition of incremental Handoffs sent to a verified existing session;
- the canonical Worktree Fingerprint encoding, race-free Review Target construction, and minimum ancestry rules for safely adopting an existing commit;
- whether conflict resolution uses a distinct agent role and session policy or a specialized Implementer pass;
- the post-stabilization backward-compatibility and version-evolution policy for Result Envelopes;
- the configuration and failure semantics of any later deterministic post-review validation pipeline;
- the Managed Agent Pass Budget's broader saved-configuration scope, a possible elapsed-agent-time budget, and provider usage-window behavior;
- retry, interruption, cancellation, and recovery behavior, including the mapping from blocker classes to the small recovery-action vocabulary;
- whether mode changes persist for later passes and whether usage confirms the provisional harness behavior, without adding arbitrary override-lifetime machinery;
- final commit construction and failure handling.
